## Testing

Everything below runs **offline** — no RPC, no API key, no funds:

```bash
npm install
npm test          # both packages — 16 tests
npm run typecheck
```

```bash
cd contracts
forge install foundry-rs/forge-std --no-git   # first time only; lib/ is gitignored
forge test -vv                                # 9 tests, incl. fuzz
```

### On-chain checks (need `spike/.env` + funds)

```bash
# One real UserOp through a real bundler — proves the vendored ERC-4337 slice.
set -a && . spike/.env && set +a
node packages/wallet/scripts/live-e2e.mjs

# The original week-1 spike: identity -> wallet -> x402 -> attestation.
```

## Keeping the three repos in step

This repo is the one that moves; the other two follow it. Clone all three as
siblings — the examples resolve the packages through `file:` paths and the docs
site syncs prose from here, so both expect the layout below.

```
your-workspace/
├── chainbridge/            # this repo
├── chainbridge-examples/
└── chainbridge-docs/
```

**After a change here is final and its tests pass**, update both downstream
repos before calling the work done:

| | Repo | Do this |
|---|---|---|
| 1 | `chainbridge` | Land the change. `npm test` and `npm run build` must be green. |
| 2 | `chainbridge-examples` | Rebuild against it, run both examples end to end, fix any API drift. |
| 3 | `chainbridge-docs` | `npm run sync`, update the hand-written pages describing the changed API, `npm run check`, commit the regenerated `content/`. |

That order is not arbitrary. The examples are the first thing that notices a
broken public API — they consume the packages as a customer does, with no
workspace resolution to paper over a missing export. The docs should then
describe what the examples actually proved, not what the API was intended to do.

The docs site deploys from its own committed snapshot of this repo's prose, so
skipping step 3 ships stale documentation without failing anything locally. Its
CI checks out both repos and re-runs the sync to catch exactly that.
